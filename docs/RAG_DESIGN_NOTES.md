# RAG 챗봇 설계 아이디어 노트 (계층형 타게팅)

본 문서는 RAG 기반 규정 Q&A 챗봇 PoC의 설계 아이디어와 논의 결과를 계속 기록하는 노트입니다. 확정된 사항은 본문에 반영하고, 날짜별 결정 내용은 §8 변경 이력에 남깁니다.

- **관련 문서**: [POLICY_KNOWLEDGE_INDEX.md](POLICY_KNOWLEDGE_INDEX.md) (지식 카드·목차 라우팅), [MCP_TOOL_DESIGN.md](MCP_TOOL_DESIGN.md) (계산·판정 도구 명세)
- **상태**: 설계 논의 중 (구현 전)

---

## 1. 개요

### 1.1 제안 구조

| 단계 | 내용 |
| :---: | :--- |
| 1 | **문서 용도 DB**: 전처리할 때 문서별 용도(어떤 질문에 쓰는 문서인지)를 DB에 저장합니다 |
| 2 | **문서 타게팅**: 오케스트레이터 LLM이 문서 목록(용도)을 보고 참조할 문서를 직접 고릅니다 |
| 3 | **청크 타게팅**: 선택된 문서의 정보 덩어리(청크) 목록을 보고 필요한 청크를 직접 고릅니다 |
| 4 | **문서별 도구**: 선택된 문서에서 쓸 수 있는 MCP 도구 목록을 받아, 필요하다고 판단하면 호출합니다 |
| 5 | **멀티턴 역질문**: 도구 호출에 필요한 정보가 부족하면 사용자에게 되물어 확보합니다 |

### 1.2 기존 설계와의 관계

[POLICY_KNOWLEDGE_INDEX.md](POLICY_KNOWLEDGE_INDEX.md)의 목차 라우팅을 기반으로 합니다. 그 문서 §8의 "문서별 상위 목차 + 카드 목차 2계층화"를 처음부터 적용하고, **문서 단위로 도구를 노출**하는 구조를 더한 형태입니다. 청크는 그 문서의 "지식 카드"에 해당하지만, 100종 이상을 손으로 만들 수 없으므로 PDF를 자동으로 나눈 **3계층(문서 요약 → parent → child, §5.3)**으로 만듭니다. 카드 작성 원칙(자기완결, 표·예외 보존)은 분할 규칙에 반영합니다.

---

## 2. 설계 판단

방향은 맞습니다. 소수의 규정 문서, 이미지 속 수치, 예외 조항, 계산 도구가 필요한 이 도메인에서는 일반 벡터 RAG보다 유리합니다.

| 장점 | 설명 |
| :--- | :--- |
| 도구 선택 혼선 감소 | 선택된 문서의 도구만 보여주므로 후보가 줄어듭니다. 범용 도구를 제거했더니 도구 선택이 정확해진 기존 경험과 같은 방향입니다 |
| 수치·예외 보존 | 구조(장·절·조·표) 기준으로 나누어 예외 조항이 청크 경계에서 잘리지 않게 하고, 수치가 들어간 청크는 사람이 검증해 이미지 속 숫자 누락을 막습니다 |
| 근거 추적 | 답변에 문서 ID·청크 ID·쪽번호를 근거로 표시할 수 있습니다 |
| 낮은 구축 비용 | 임베딩 인프라 없이 PoC를 시작할 수 있고, 목차가 정적 텍스트라 프롬프트 캐시에 유리합니다 |

다만 **문서·청크 선택이 한 번 빗나가면 복구할 경로가 없는 구조**이므로, §3·§4의 보완이 필요합니다.

## 3. 위험과 보완

| # | 위험 | 보완 |
| :---: | :--- | :--- |
| 1 | **라우팅 실패 = 답변 실패** | 검색으로 후보를 넓게 잡고, 여러 개 선택, 카테고리 펼치기, "참조문서 없음" 선택지. 상세 흐름은 §4 |
| 2 | **용도 메타데이터 품질이 사실상 검색 엔진** | 용도 한 줄로는 부족합니다. `summary`(판단에 필요한 수치·조건 포함), `keywords`(구어·동의어), `questions`(예상 질문), `not_for`(헷갈리는 이웃 문서)를 둡니다. `questions`는 라우팅 평가셋으로 재사용합니다 |
| 3 | **단계마다 LLM 호출 → 지연·컨텍스트 증가** | seed32-think는 요청당 32K 토큰, 동시 4요청 제약이 있습니다. 32K는 모델 한계(128K)가 아니라 서버 설정(`max_model_len=32768`)이며, 늘리면 동시 처리 수가 줄어듭니다(§5.3.1). 문서 → 청크 → 도구 → 답변이면 한 턴에 3~4회 호출합니다. 문서가 5종 미만(목차 8K 토큰 미만)일 때는 문서·청크 목차를 한 번에 주고 한 번에 고르게 하고, 계층 분리는 규모가 커진 뒤에 합니다. 청크 본문은 선택된 것만 넣고, 대화가 길어지면 이전 턴 원문은 요약하거나 제거합니다 |
| 4 | **문서별 도구의 경계 사례** | 문서 두 개에 걸친 질문(예: 교육 + 여비)이 있으므로 도구 ↔ 문서는 N:M 관계로 저장하고, 선택된 문서들의 도구를 합쳐서 노출합니다. 선택한 문서·도구 목록은 그래프 state(checkpointer)에 저장합니다. 역질문에 대한 답("3시간이요")만 보고 다시 라우팅하면 다른 문서로 튈 수 있기 때문입니다 |
| 5 | **멀티턴 슬롯 채우기** | 정보 누락 판정은 LLM이 아니라 도구가 합니다 (현재 `need_info` 방식 유지). LLM은 추측한 값으로 인자를 채우지 않습니다. 확인된 값은 state에 쌓고, 주제가 바뀌면 비우고, 역질문은 2회 정도로 제한한 뒤 조건을 달아 답합니다. 이미 나온 값이나 유도할 수 있는 값은 다시 묻지 않습니다 |
| 6 | **청크 설계** | 의미 단위로 자르고, 표는 통째로 두고, 예외는 본 조항과 같은 청크에 둡니다. 청크 하나만 읽어도 답할 수 있게(자기완결) 작성하고, `related` 링크로 이웃 청크를 추가 조회합니다. 자동 분할 규칙은 §5.3 |
| 7 | **루프 제어·버전 관리** | 조회·도구 호출 횟수에 상한을 두고, 답하기 전에 근거가 충분한지 점검합니다. 문서마다 버전, `effective_date`, `verified`를 기록하고, 청크에 적힌 수치와 도구가 쓰는 수치가 같은지 테스트합니다 |

## 4. 라우팅 흐름 (확정)

대상 문서가 **100종 이상**이 될 예정이므로, 목차 전체를 프롬프트에 넣지 않고 **검색으로 후보를 먼저 좁힌 뒤 LLM이 고르는** 구조로 확정합니다. 라우터는 planner와 분리된 별도 노드입니다.

### 4.1 단계

| 단계 | 조건 | 동작 |
| :---: | :--- | :--- |
| 0 | 처음부터 범위 밖인 질문 (인사말, 개인 잔액 조회 등) | 검색 없이 바로 **참조문서 없음**. 검색 한 번이 LLM 호출 한 번이라 지연을 줄입니다 |
| 1 | 기본 | **문서 카탈로그 하이브리드 검색**(BM25 + 벡터)으로 후보 문서 10~20개를 추립니다 |
| 2 | 기본 | 라우터 LLM이 **카테고리 목록 + 검색 후보(카테고리 표시)**를 함께 보고 문서를 **최대 3개** 선택합니다 (thinking off, 짧은 호출) |
| 2-1 | 검색 후보가 맞지 않을 때 | 카테고리를 지정해 그 카테고리의 문서 목록을 펼쳐 봅니다. 이때만 호출이 하나 늘어납니다 |
| 3 | 문서 선택 후 | planner가 선택된 문서의 **parent 요약 목록**(청크 검색 적중 표시)과 도구만 보고 계획을 세웁니다. agent가 child 원문(앞뒤 이웃 포함)을 조회하고, 필요할 때만 parent 전체를 엽니다 |
| 3-1 | 열어 본 청크가 근거로 부족할 때 | 라우터로 돌아가 다른 후보를 찾습니다 (상한 1회) |
| 4 | 끝까지 찾지 못했을 때 | **참조문서 없음**을 선택합니다. 억지로 맞추지 않고, 규정에 없다는 것과 담당 부서를 안내합니다 |

- 선택한 문서·도구 목록은 state에 저장하고, 역질문 후 다음 턴에도 다시 라우팅하지 않고 이어서 씁니다.

### 4.2 검색 방식

- **하이브리드**(BM25 + 벡터)로 시작합니다. 첫 단계 재현율이 전체 정확도를 좌우하는데, "기름값"과 "자동차 운임"처럼 사용자 표현과 규정 용어가 다른 경우를 BM25만으로는 놓치기 쉽기 때문입니다.
- 임베딩 대상은 문서 본문이 아니라 **용도 메타데이터**(`summary`·`keywords`·`questions`)입니다. 청크 단계 검색은 child 청크(문맥 머리말 + 본문)와 parent 요약을 대상으로 합니다(§5.3). 수치가 이미지에만 있는 PDF는 자동 추출에서 숫자가 빠질 수 있으므로, 수치가 들어간 청크는 사람이 검증합니다.
- 검색 도구 인터페이스(`search(query, category?)` → 문서·청크 목록)는 처음부터 고정해, 검색 엔진을 바꿔도 그래프는 그대로 두게 합니다.

### 4.3 카테고리

- **사용자 관점의 주제**로 나눕니다 (예: 출장·여비, 교육, 급여·세무). 부서 조직도로 나누지 않고, 담당 부서는 문서의 속성으로 둡니다. 사용자는 소관 부서를 모르는 경우가 많고(여비는 회계로 생각하기 쉽지만 담당은 상생복지팀), 조직 개편 때도 카테고리를 유지할 수 있습니다.
- 문서 하나가 여러 카테고리에 속할 수 있고, 라우터도 여러 카테고리를 고를 수 있습니다.
- 카테고리는 별도 LLM 단계가 아니라 **라우터 호출 안의 정보이자 검색이 빗나갔을 때의 두 번째 경로**입니다.
- **용도 목록 페이징은 쓰지 않습니다.** 페이지를 넘기느라 호출이 늘고, 페이지 사이의 문서를 비교할 수 없으며, 앞 페이지에서 그럴듯한 문서를 보면 멈추는 경향이 있기 때문입니다.
- 실제 분류는 100종 문서 목록이 확보되면 정합니다.

### 4.4 흐름도

```text
질의
 ├─ 범위 밖? ─────────────────────────────────────▶ 참조문서 없음 → 담당 부서 안내
 ▼
[라우터] 하이브리드 검색 → 후보 10~20개 (카테고리 표시)
 ▼
LLM 선택 (카테고리 목록 + 후보)
 ├─ 후보가 맞지 않음 → 카테고리 문서 목록 펼치기 ─┐
 ├─ 해당 없음 ───────────────────────────────────┼▶ 참조문서 없음 → 담당 부서 안내
 ▼                                               │
선택 문서 최대 3개 → state 저장 ◀─────────────────┘
 ▼
[planner] 선택 문서의 청크 목록 + 도구로 계획
 ▼
[agent] 청크 원문 조회 ── 근거 부족 → 라우터로 (1회)
 ▼
도구 호출 / 역질문 / 답변
```

## 5. 권장 전체 흐름

```text
질의 → [router] 하이브리드 검색 → 문서 최대 3개 선택 (카테고리 펼치기 / 참조문서 없음)
     → state에 selected_docs / tools / slots 저장
     → [planner] 선택 문서의 청크 목록·도구로 계획
     → [agent] get_chunks(ids) → 문서별 도구 바인딩 → 호출
          ↳ need_info → 역질문 (최대 2회) → 다음 턴은 같은 state로 재개
     → 근거(문서·청크·쪽) 표시하여 답변
```

### 5.1 결정 사항 요약

| 항목 | 결정 |
| :--- | :--- |
| 라우터 | planner와 분리된 별도 노드. 검색으로 좁힌 후보에서 LLM이 최대 3개 선택 |
| 카탈로그 저장소 | 실제 DB (문서·청크·도구·카테고리 테이블, 문서↔도구·문서↔카테고리 N:M). 검색 인덱스(BM25·벡터) 포함 |
| 검색 | 하이브리드(BM25 + 벡터), 임베딩 대상은 용도 메타데이터 |
| 역질문 | 최대 2회. 그래도 부족하면 "~인 경우 ○○, ~인 경우 △△"처럼 경우를 나눠 조건부로 답변 |
| 임베딩 모델 | `dragonkue/bge-m3-ko` (BGE-M3 한국어 파인튜닝) |
| RDB | PostgreSQL: 문서·청크·도구·카테고리·매핑·버전·검증 상태의 **원본** |
| Vector DB | Qdrant: 검색 전용 **인덱스**. 원본에서 다시 만들 수 있어야 합니다 |
| 청킹 | 문서 요약 → parent(기본 2~4K) → child(512 상한) 3계층. 구조 기반 분할, 크기 상한은 전처리 설정으로 조정 (§5.3) |
| 컨텍스트 기준 | 요청당 32K(현재 서버 설정). 원문은 적중 child + 앞뒤 이웃을 기본으로 넣습니다 |

### 5.2 저장소 역할 분담

| 구분 | PostgreSQL (원본) | Qdrant (검색 인덱스) |
| :--- | :--- | :--- |
| 담는 것 | 문서, 청크 본문, 메타데이터(`summary`·`keywords`·`questions`·`not_for`), 도구, 카테고리, 문서↔도구·문서↔카테고리 N:M, 버전·`effective_date`·`verified` | dense 벡터 + sparse(키워드) 벡터, 필터용 payload(`doc_id`, `category_ids`, `verified`, `effective_date`) |
| 조회 | ID로 원문·도구 목록 조회 (`get_chunks`, `list_docs`) | `search(query, category?)` |
| 쓰기 | 사람이 검증·수정 | 동기화 작업만 씀 (직접 수정 금지) |

- **컬렉션 2개**: `doc_catalog`(문서 선택용), `chunks`(청크 검색용). `chunks`에는 child 포인트와 parent 요약 포인트를 함께 넣고 payload `type`(`child`/`parent`)으로 구분합니다.
- **문서 하나에 포인트 여러 개**: `doc_catalog`에는 `summary` 포인트 1개 + 예상 질문마다 포인트 1개를 넣고, 검색 시 `doc_id`로 그룹화(Qdrant group 조회)해서 문서 단위로 후보를 뽑습니다. 질문형 사용자 질의가 예상 질문과 가장 잘 맞기 때문에 재현율이 오릅니다.
- **동기화**: PostgreSQL 행마다 `content_hash`를 두고, 바뀐 행만 다시 임베딩해서 Qdrant에 upsert합니다. Qdrant 포인트 ID는 PostgreSQL의 청크·문서 ID에서 결정적으로 만듭니다 (예: UUIDv5). 문서가 폐지되면 해당 `doc_id` 포인트를 삭제합니다.
- **한국어 키워드 검색 (확정)**: Kiwi 형태소 분석 + 해시 기반 sparse 인덱스로 BM25를 만들어 Qdrant sparse 벡터에 넣습니다. 일반 BM25 토크나이저는 조사·어미를 분리하지 못해 "출장비를"과 "출장비"가 다른 단어가 되기 때문입니다.
  - **해시 함수**: 프로세스마다 값이 바뀌지 않는 안정 해시(예: mmh3, xxhash)를 씁니다. Python 내장 `hash()`는 실행할 때마다 값이 달라져(`PYTHONHASHSEED`) 색인과 질의의 인덱스가 어긋납니다. Qdrant sparse 인덱스가 uint32이므로 32비트 해시를 쓰면 충돌은 무시할 수준입니다
  - **가중치**: 문서 쪽에는 BM25의 TF 포화·문서 길이 보정(k1, b)을 적용한 값을 넣고, IDF는 Qdrant의 IDF modifier에 맡깁니다. 질의 쪽은 토큰별 가중치 1로 넣습니다
  - **토큰화 일관성**: 색인과 질의에 같은 Kiwi 버전·옵션·품사 필터(예: 일반·고유명사, 동사·형용사 어근, 외국어, 숫자)를 씁니다. 규정 용어(예: 자가용 운임, 시외당일귀임)는 사용자 사전에 등록합니다. 토크나이저 설정이 바뀌면 sparse 인덱스 전체를 다시 만듭니다
  - `dragonkue/bge-m3-ko`는 dense 전용입니다. 로컬 캐시에 BGE-M3 원본에 있는 `sparse_linear.pt`·`colbert_linear.pt`가 없으므로 모델 자체의 sparse 출력은 쓸 수 없습니다
- **결합**: dense와 sparse 결과를 Qdrant Query API의 RRF로 합칩니다.
- **임베딩 서빙**: PoC에서는 로컬에 받아 둔 `dragonkue/bge-m3-ko`(Hugging Face 캐시)를 sentence-transformers로 직접 불러 씁니다. DGX로 옮길지는 미정이며, 옮길 때는 LLM 서버의 동시 4요청 슬롯을 쓰지 않도록 별도 프로세스(vLLM embed 모드 또는 TEI)로 띄웁니다. 호출부는 `embed(texts)` 인터페이스로 감싸 두어 위치가 바뀌어도 코드는 그대로 둡니다

### 5.3 PDF 청킹·요약 계층 (확정)

사람이 검증한 지식 카드를 100종 이상 만들 수 없으므로, PDF를 자동으로 **3계층**으로 나눕니다. 각 계층은 §4 라우팅 흐름의 단계 하나씩을 맡습니다.

| 계층 | 크기 | 쓰는 곳 | 내용 |
| :--- | :--- | :--- | :--- |
| 문서 요약 | 1개/문서 | 라우터 (`doc_catalog`) | `summary`·`keywords`·`questions`·`not_for`. 본문이 32K에 들어가는 문서(약 50쪽 이하)는 본문 전체로 한 번에 만들고, 넘는 문서만 parent 요약을 합성(map-reduce)해서 만듭니다 (§5.3.5 문서 크기) |
| parent | 기본 2~4K (child 4~8개) | planner의 청크 목록, 필요할 때 원문 | 장·절·조 단위 묶음 + **라우팅용 요약** |
| child | 512 토큰 상한 | 벡터·BM25 검색, 근거 표시 | 원문 조각 + 문맥 머리말, 쪽번호 |

#### 5.3.1 parent 크기와 컨텍스트 기준

처음 제안은 child 10~20개를 묶은 약 10K parent였으나, 아래 이유로 **기본 2~4K**로 정했습니다.

- **컨텍스트**: seed32-think 서버는 요청당 32K입니다. 10K parent를 문서 3개에서 하나씩만 넣어도 도구 목록·대화 이력·Thinking과 합쳐 한도를 넘습니다.
- **32K의 근거 (기술 검토)**: 모델 카드 기준 HyperCLOVAX-SEED-Think-32B는 128K를 지원합니다(`text_config.max_position_embeddings=131072`, rope_scaling 없음). 서버(vLLM `/v1/models`)는 `max_model_len=32768`로 설정되어 있습니다. 즉 32K는 **서버 설정값**입니다.
- **확장 시 트레이드오프**: KV 캐시는 토큰당 약 288KiB입니다(KV head 8 × 72층 × head_dim 128 × BF16, config 값으로 계산). 요청 하나가 32K면 약 9GiB, 128K면 약 36GiB이므로, GPU 메모리가 같다면 128K에서는 동시 처리 수가 4개에서 1개 안팎으로 줄어듭니다. 길이를 늘려도 prefill 지연이 늘고 긴 문맥 속 수치를 놓칠 위험이 남습니다.
- **원문 주입 기본값**: parent 전체가 아니라 **적중 child + 앞뒤 이웃 child**를 넣고, parent 전체는 필요할 때만 조회합니다.
- **전처리 설정으로 상한 조정**: 서버 컨텍스트를 늘리면 설정만 바꿔 다시 전처리합니다.

| 설정 | 기본값 | 의미 |
| :--- | :---: | :--- |
| `CHUNK_CHILD_MAX_TOKENS` | 512 | child 상한 (표·단서 조항은 넘을 수 있음) |
| `CHUNK_PARENT_MAX_TOKENS` | 4096 | parent 상한 |
| `CHUNK_PARENT_MIN_TOKENS` | 1024 | 짧은 조문을 이웃과 합치는 하한 |
| `CHUNK_NEIGHBOR_WINDOW` | 1 | 적중 child 앞뒤로 함께 넣을 child 수 |

- 토큰 수는 **seed32-think 토크나이저** 기준으로 셉니다. 컨텍스트 예산이 이 모델 기준이기 때문입니다. `bge-m3-ko`는 8K까지 받으므로 child 512는 임베딩 쪽 한도에 여유가 있습니다.
- 문서마다 적용한 설정(상한·토크나이저·파서 버전)을 `chunking_config`로 PostgreSQL에 기록합니다. 설정이 바뀌면 해당 문서를 다시 나누고 다시 임베딩할 대상으로 판정합니다.

#### 5.3.2 분할·요약 규칙

| # | 규칙 | 이유 |
| :---: | :--- | :--- |
| 1 | **구조 기반 분할**: 장·절·조·항 경계를 먼저 쓰고, 512는 상한으로만 씁니다. parent도 개수가 아니라 장·절·조 경계로 묶습니다 | 고정 크기로 자르면 조문 중간이 끊깁니다 |
| 2 | **표·단서 조항은 자르지 않습니다**: 표는 통째로 child 하나로 두고(상한 초과 허용), "단, …"은 본 조항과 같은 child에 둡니다 | §3-6. 예외가 다른 청크로 떨어지면 틀린 답이 나옵니다 |
| 3 | **문맥 머리말**: 임베딩·BM25에 넣는 텍스트 앞에 `문서명 > 장 > 조` 경로와 parent 요약 한 줄을 붙입니다 (원문 저장 시에는 분리) | "② 단, 위의 경우는…" 같은 child도 단독으로 검색되게 합니다 |
| 4 | **parent 요약은 라우팅용 구조화 필드**로 만듭니다: `covers`(다루는 주제·조건·핵심 수치), `not_covers`(헷갈리는 이웃 parent·문서), `keywords`(구어·동의어), `questions`(예상 질문) | 산문 요약으로는 오케스트레이터가 "이 문맥이 필요한가"를 판단하기 어렵습니다. 문서 메타데이터(§3-2)와 같은 형식입니다 |
| 5 | **수치 부분 검증**: 수치가 들어간 child와 그 parent 요약만 사람이 검증합니다(`verified`) | 이미지·표 속 숫자 누락이 가장 큰 위험이고, 전체 검증은 100종 규모에서 불가능합니다 |

#### 5.3.3 파이프라인

```text
PDF
 ▼ 파싱 (쪽 이미지 → seed32-think 비전 → 마크다운, 텍스트 레이어와 대조)
 ▼ 쪽 이어 붙이기 → 번호 패턴·목차로 제목 수준 재부여
구조 트리 (장 > 절 > 항목, 표, 쪽번호)
 ▼ 구조 기반 분할 (CHUNK_CHILD_MAX_TOKENS)
child 목록 ──▶ 장·절·조 경계로 묶기 (CHUNK_PARENT_MIN/MAX_TOKENS) ──▶ parent 목록
 ▼
parent 요약 (LLM, covers / not_covers / keywords / questions)
 ▼
문서 요약 (본문 전체, 32K 초과 시 parent 요약 합성, summary / keywords / questions / not_for)
 ▼
검증 (수치 포함 child·요약 → 사람, verified)
 ▼
PostgreSQL 저장 ──▶ 동기화 작업 ──▶ Qdrant (doc_catalog: 문서 요약, chunks: child + parent 요약)
```

- **PostgreSQL**: `documents`(문서 요약, `chunking_config`) → `sections`(parent: 구조 경로, 쪽 범위, 요약 필드) → `chunks`(child: 본문, 순번, 쪽번호, `parent_id`). 답변 근거는 child의 쪽번호로 표시합니다.
- **검색 결과 묶기**: `chunks` 검색 결과를 `parent_id`로 그룹화해서 planner에 "parent 요약 + 적중 child 표시"로 보여 줍니다. parent 요약 포인트도 함께 검색해서 질문형 질의의 재현율을 보강합니다.
- **PDF 파서**: seed32-think 비전으로 쪽 이미지를 마크다운으로 옮겨 적고, 텍스트 레이어는 검증 대조본으로 씁니다. `DOC_PARSER_BASE_URL`(Docling Serve)은 본문 수치를 살리지 못했습니다 (§5.3.5).

#### 5.3.4 실측 과제

보유 PDF 2종(개인교육훈련비, 여비업무 처리기준)으로 먼저 확인합니다.

- child·parent 토큰 분포, 상한을 넘은 표의 크기
- 표·단서 조항이 경계에서 잘렸는지
- 이미지 속 수치가 추출에서 빠졌는지 (기존 수작업 지식 카드의 수치와 대조)
- parent 요약만 보고 기존 평가 질의에 필요한 parent를 고를 수 있는지 (§6 청크 재현율)

#### 5.3.5 실측 결과 (2026-10-26, 보유 PDF 2종)

**파싱**: 여비 PDF는 본문 큰 글씨의 숫자·영문·괄호가 글자가 아니라 벡터 도형으로 그려져 있어 텍스트 레이어에 없습니다(예: "일비 원(4시간 미만)"). 정답은 [MCP_TOOL_DESIGN.md 부록 A](MCP_TOOL_DESIGN.md)의 수치(본문 18개, 표·각주 43개)로 잡았습니다.

| 방식 | 본문 수치 | 표 수치 | 비고 |
| :--- | :---: | :---: | :--- |
| 텍스트 레이어 (PyMuPDF·pdfplumber) | 8/18 | 36/43 | 연비 표는 이미지 |
| Docling Serve 기본 (`DOC_PARSER_BASE_URL`) | 8/18 | 43/43 | 텍스트 레이어를 그대로 씀 |
| Docling Serve 강제 OCR (easyocr, ko) | 13/18 | 42/43 | 굵은 핵심 수치(8,000원·50%·30%·1만원) 누락, "6Okm"·"을→올" 오인식, 문장 누락 |
| Docling Serve VLM 파이프라인 | — | — | 시험한 프리셋 5종(기본·mineru2_pro·dots_ocr·glm_ocr·qwen) 모두 서버 오류 |
| **seed32-think 비전 (쪽 이미지 150dpi → 마크다운)** | **18/18** | **43/43** | 한글 누락 0.2%(텍스트 레이어 대비), 지어낸 내용 없음. VLM에만 있는 글자는 병합 셀 반복과 이미지 표였습니다 |

- **파싱 방식 (결정)**: seed32-think에 쪽 이미지를 넣고 thinking을 끈 채 마크다운으로 옮겨 적게 합니다. 22쪽에 입력 59.9K(쪽당 이미지 2,723 토큰 고정), 출력 10.1K 토큰, 쪽당 약 18초, 동시 3요청으로 약 2.5분이 걸렸습니다. 100종 × 20쪽으로 잡으면 입력 약 540만, 출력 약 90만 토큰, 약 3시간짜리 오프라인 배치입니다. 출력량이 문서 길이와 같아서 **전처리 비용은 대부분 이 옮겨 적기 단계에서 나옵니다**.
- 텍스트 레이어는 버리지 않고 **검증용 대조본**으로 씁니다. 한글이 크게 어긋나는 쪽(유사도 0.97 미만)을 사람 검증 대상으로 올립니다.

**문서 크기**: 여비 20쪽이 9,449 토큰, 교육훈련비 2쪽이 902 토큰입니다(seed32-think 토크나이저, 서버 `prompt_tokens`와 일치 확인). 쪽당 약 470 토큰이므로 **약 50쪽 이하 문서는 32K 한 번에 들어갑니다**. 이런 문서는 문서 요약을 map-reduce 없이 본문 전체로 한 번에 만듭니다.

**구조**: 두 문서 모두 `제N조` 체계가 없습니다. 번호 체계는 `Ⅰ`·`참고N`·`[양식N]`(장) → `1.` → 네모 숫자·`①`·`➎`(절) → `○`·`-`·`① (운임)`(항목)입니다.
- 쪽마다 따로 옮겨 적으면 VLM이 매기는 `#` 수준이 쪽마다 다릅니다(같은 급인 "1 시내출장"은 `##`, "3 특별당일귀임"은 `#`). 제목 수준은 **번호 패턴과 1쪽 목차**로 다시 매깁니다. VLM이 빠뜨린 "[양식 1]" 꼬리표도 목차와 맞춰 장으로 잡습니다.
- 문장이 쪽을 넘어갑니다("공단 숙소… 1야당" / "2만원 지급"). **쪽을 이어 붙인 뒤에 나누고**, 쪽번호는 child마다 범위로 기록합니다. 여비 문서의 child 33개 중 6개가 두 쪽에 걸칩니다.

**분할 결과** (child 상한 512, parent 1024~4096)

| 문서 | child | child 토큰 (중앙값 / 최대) | 512 초과 | parent | parent 토큰 |
| :--- | :---: | :---: | :--- | :---: | :--- |
| 여비 | 33 | 250 / 739 | 4개, 모두 표 (513~739) | 11 | 193~2,773 (Ⅲ 출장유형별만 1,024 이상) |
| 교육훈련비 | 7 | 37 / 363 | 없음 | 2 | 363, 482 |

- 문맥 머리말(`문서명 > 장 > 절`)은 child당 중앙값 30 토큰입니다.
- 장 경계를 넘어 합치지 않으므로 이 문서들에서는 parent 대부분이 하한(1,024)보다 작습니다. 문서 전체가 parent 하한보다 작으면(교육훈련비) parent 하나로 둡니다.

**실측에서 추가한 분할 규칙** (모두 규칙 기반이라 LLM 비용 없음)

| 규칙 | 없을 때 생긴 문제 |
| :--- | :--- |
| `①~⑳` 하위 항목에서 child를 새로 시작 (현재 child가 128 토큰 이상일 때) | 크기로만 묶었더니 "② (숙박료)" 본문과 "상한 초과 시 30% 추가 지급"이 다른 child로 갈라졌습니다 |
| `<제목>` 줄은 바로 뒤 목록·표와 한 단위 | `<공무형편상 부득이한 사유>` 목록이 두 child로 나뉘었고, `<출장경비 지출 증빙서류>` 제목과 표가 떨어졌습니다 |
| 글머리 없는 줄·`*`·`※`·`단,`·`다만`은 앞 항목에 붙이기 (쪽을 넘어가도) | 쪽 경계에서 문장이 잘렸습니다 |

- 남은 정리 과제: 아주 작은 child(총칙 "2. 근거" 6 토큰 등)는 같은 parent 안의 이웃과 합칩니다. 1쪽 목차 child는 검색 대상에서 뺍니다.
- **제목만으로는 라우팅할 수 없는 사례**: 교육훈련비의 학점 지급 기준(➒ 이수학점)은 "(참고용) 개인교육훈련비 신청방법" 아래에 있습니다. 신청 화면의 입력 항목 설명이기 때문입니다. parent 요약의 `covers`에 실제 내용("학점 지급 기준·계산 예시")을 적어야 하는 이유입니다(§5.3.2 규칙 4).

**고정 길이 분할과 비교** (토큰 512, overlap 64, 같은 마크다운)

| 항목 | 고정 길이 | 구조 기반 |
| :--- | :---: | :---: |
| 표가 잘림 | 16개 중 7개 | 0 (상한 초과 허용) |
| 단서가 딸린 항목이 잘림 | 10개 중 0개 | 0 |
| 일반 항목이 잘림 | 96개 중 1개 | 0 |

- 이 문서들에서는 단서가 본문 바로 뒤 한두 줄이라 overlap으로도 지켜졌습니다. **고정 길이 분할의 실제 피해는 표**입니다(국외 체재비 표, 국가·도시 등급표 등).

### 5.4 구현 순서

1. **임베딩·sparse 모듈**: 로컬 `dragonkue/bge-m3-ko`로 `embed(texts)`, Kiwi + 안정 해시로 `sparse(texts)`를 만듭니다
2. **PostgreSQL 스키마·Qdrant 컬렉션**: §5.2 역할 분담대로 만들고, 동기화 작업을 작성합니다. 기존 2종(교육훈련비, 여비)을 첫 데이터로 이관합니다
3. **청킹·요약 파이프라인**: §5.3.3 순서대로 PDF를 child/parent로 나누고, LLM이 parent 요약과 문서 요약(`summary`·`keywords`·`questions`·`not_for`) 초안을 만든 뒤, 수치가 들어간 청크와 요약을 사람이 검증합니다. 보유 PDF 2종으로 먼저 실측합니다(§5.3.4)
4. **검색 도구**: `search(query, category?)`, `list_docs(category)`, `get_chunks(ids)`를 MCP 서버에 추가합니다
5. **router 노드**: `graph.py`에 planner 앞 노드로 추가하고, 선택 결과를 state에 저장합니다
6. **문서별 도구 바인딩**: 선택된 문서의 도구만 agent에 바인딩합니다
7. **역질문 상한·조건부 답변**: state에 역질문 횟수를 두고 프롬프트 규칙에 반영합니다
8. **평가셋·회귀 측정**: §6 지표

## 6. 평가

[POLICY_KNOWLEDGE_INDEX.md §7](POLICY_KNOWLEDGE_INDEX.md)의 지표를 확장해서 사용합니다.

| 지표 | 정의 |
| :--- | :--- |
| 검색 재현율@20 | 하이브리드 검색 후보 20개 안에 기대 문서가 포함된 비율. 이 단계에서 빠지면 뒤에서 복구할 수 없으므로 가장 먼저 봅니다 |
| 문서 재현율@3 | 라우터가 선택한 문서(최대 3개)에 기대 문서가 포함된 비율 |
| 청크 재현율@3 | 선택한 청크(최대 3개)에 기대 청크가 포함된 비율 |
| 첫 도구 정확도 | 첫 도구 호출이 기대 도구와 일치하는 비율 |
| 역질문 적정성 | 정보가 부족한 질의에서 계산 대신 역질문을 한 비율 |
| 참조문서 없음 정확도 | 범위 밖·규정 공백 질의에서 억지 매칭 없이 "참조문서 없음"을 고른 비율 |
| 근거 표시율 | 규정 답변에 출처를 표시한 비율 |

- 헷갈리는 쌍(시내/시외 출장, 토익 학원비/토익 학점)과 **문서 두 개에 걸친 질의**를 평가셋에 반드시 넣습니다.
- 사용자 표현과 규정 용어가 다른 질의("기름값")를 넣어 벡터 검색이 실제로 보완하는지 확인합니다.
- 라우팅 정확도는 문서 수에 크게 좌우되므로, 2종으로 측정한 결과는 100종에서의 성능을 대표하지 못합니다. 실제 문서를 최소 수십 종 확보한 뒤 측정합니다.
