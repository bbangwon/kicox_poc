# RAG 챗봇 설계 아이디어 노트 (계층형 타게팅)

본 문서는 RAG 기반 규정 Q&A 챗봇 PoC의 설계 아이디어와 논의 결과를 계속 기록하는 노트입니다. 확정된 사항은 본문에 반영하고, 날짜별 결정 내용은 §8 변경 이력에 남깁니다.

- **관련 문서**: [POLICY_KNOWLEDGE_INDEX.md](POLICY_KNOWLEDGE_INDEX.md) (지식 카드·목차 라우팅), [MCP_TOOL_DESIGN.md](MCP_TOOL_DESIGN.md) (계산·판정 도구 명세)
- **상태**: 설계 논의 중 (구현 전)

---

## 1. 개요

### 1.1 제안 구조

| 단계 | 내용 |
| :---: | :--- |
| 1 | **문서 용도 DB**: 전처리할 때 문서별 용도(어떤 질문에 쓰는 문서인지)를 DB에 저장합니다 |
| 2 | **문서 타게팅**: 오케스트레이터 LLM이 문서 목록(용도)을 보고 참조할 문서를 직접 고릅니다 |
| 3 | **청크 타게팅**: 선택된 문서의 정보 덩어리(청크) 목록을 보고 필요한 청크를 직접 고릅니다 |
| 4 | **문서별 도구**: 선택된 문서에서 쓸 수 있는 MCP 도구 목록을 받아, 필요하다고 판단하면 호출합니다 |
| 5 | **멀티턴 역질문**: 도구 호출에 필요한 정보가 부족하면 사용자에게 되물어 확보합니다 |

### 1.2 기존 설계와의 관계

[POLICY_KNOWLEDGE_INDEX.md](POLICY_KNOWLEDGE_INDEX.md)의 목차 라우팅을 기반으로 합니다. 그 문서 §8의 "문서별 상위 목차 + 카드 목차 2계층화"를 처음부터 적용하고, **문서 단위로 도구를 노출**하는 구조를 더한 형태입니다. 청크는 그 문서의 "지식 카드"와 같은 개념이며, 카드 작성 규칙(§3)을 그대로 따릅니다.

## 2. 설계 판단

방향은 맞습니다. 소수의 규정 문서, 이미지 속 수치, 예외 조항, 계산 도구가 필요한 이 도메인에서는 일반 벡터 RAG보다 유리합니다.

| 장점 | 설명 |
| :--- | :--- |
| 도구 선택 혼선 감소 | 선택된 문서의 도구만 보여주므로 후보가 줄어듭니다. 범용 도구를 제거했더니 도구 선택이 정확해진 기존 경험과 같은 방향입니다 |
| 수치·예외 보존 | 사람이 검증한 청크를 쓰므로 이미지 속 숫자가 빠지거나, 예외 조항이 청크 경계에서 잘리는 문제가 없습니다 |
| 근거 추적 | 답변에 문서 ID·청크 ID·쪽번호를 근거로 표시할 수 있습니다 |
| 낮은 구축 비용 | 임베딩 인프라 없이 PoC를 시작할 수 있고, 목차가 정적 텍스트라 프롬프트 캐시에 유리합니다 |

다만 **문서·청크 선택이 한 번 빗나가면 복구할 경로가 없는 구조**이므로, §3·§4의 보완이 필요합니다.

## 3. 위험과 보완

| # | 위험 | 보완 |
| :---: | :--- | :--- |
| 1 | **라우팅 실패 = 답변 실패** | 검색으로 후보를 넓게 잡고, 여러 개 선택, 카테고리 펼치기, "참조문서 없음" 선택지. 상세 흐름은 §4 |
| 2 | **용도 메타데이터 품질이 사실상 검색 엔진** | 용도 한 줄로는 부족합니다. `summary`(판단에 필요한 수치·조건 포함), `keywords`(구어·동의어), `questions`(예상 질문), `not_for`(헷갈리는 이웃 문서)를 둡니다. `questions`는 라우팅 평가셋으로 재사용합니다 |
| 3 | **단계마다 LLM 호출 → 지연·컨텍스트 증가** | seed32-think는 요청당 32K 토큰, 동시 4요청 제약이 있습니다. 문서 → 청크 → 도구 → 답변이면 한 턴에 3~4회 호출합니다. 문서가 5종 미만(목차 8K 토큰 미만)일 때는 문서·청크 목차를 한 번에 주고 한 번에 고르게 하고, 계층 분리는 규모가 커진 뒤에 합니다. 청크 본문은 선택된 것만 넣고, 대화가 길어지면 이전 턴 원문은 요약하거나 제거합니다 |
| 4 | **문서별 도구의 경계 사례** | 문서 두 개에 걸친 질문(예: 교육 + 여비)이 있으므로 도구 ↔ 문서는 N:M 관계로 저장하고, 선택된 문서들의 도구를 합쳐서 노출합니다. 선택한 문서·도구 목록은 그래프 state(checkpointer)에 저장합니다. 역질문에 대한 답("3시간이요")만 보고 다시 라우팅하면 다른 문서로 튈 수 있기 때문입니다 |
| 5 | **멀티턴 슬롯 채우기** | 정보 누락 판정은 LLM이 아니라 도구가 합니다 (현재 `need_info` 방식 유지). LLM은 추측한 값으로 인자를 채우지 않습니다. 확인된 값은 state에 쌓고, 주제가 바뀌면 비우고, 역질문은 2회 정도로 제한한 뒤 조건을 달아 답합니다. 이미 나온 값이나 유도할 수 있는 값은 다시 묻지 않습니다 |
| 6 | **청크 설계** | 의미 단위로 자르고, 표는 통째로 두고, 예외는 본 조항과 같은 청크에 둡니다. 청크 하나만 읽어도 답할 수 있게(자기완결) 작성하고, `related` 링크로 이웃 청크를 추가 조회합니다 |
| 7 | **루프 제어·버전 관리** | 조회·도구 호출 횟수에 상한을 두고, 답하기 전에 근거가 충분한지 점검합니다. 문서마다 버전, `effective_date`, `verified`를 기록하고, 청크에 적힌 수치와 도구가 쓰는 수치가 같은지 테스트합니다 |

## 4. 라우팅 흐름 (확정)

대상 문서가 **100종 이상**이 될 예정이므로, 목차 전체를 프롬프트에 넣지 않고 **검색으로 후보를 먼저 좁힌 뒤 LLM이 고르는** 구조로 확정합니다. 라우터는 planner와 분리된 별도 노드입니다.

### 4.1 단계

| 단계 | 조건 | 동작 |
| :---: | :--- | :--- |
| 0 | 처음부터 범위 밖인 질문 (인사말, 개인 잔액 조회 등) | 검색 없이 바로 **참조문서 없음**. 검색 한 번이 LLM 호출 한 번이라 지연을 줄입니다 |
| 1 | 기본 | **문서 카탈로그 하이브리드 검색**(BM25 + 벡터)으로 후보 문서 10~20개를 추립니다 |
| 2 | 기본 | 라우터 LLM이 **카테고리 목록 + 검색 후보(카테고리 표시)**를 함께 보고 문서를 **최대 3개** 선택합니다 (thinking off, 짧은 호출) |
| 2-1 | 검색 후보가 맞지 않을 때 | 카테고리를 지정해 그 카테고리의 문서 목록을 펼쳐 봅니다. 이때만 호출이 하나 늘어납니다 |
| 3 | 문서 선택 후 | planner가 선택된 문서의 청크 목록과 도구만 보고 계획을 세웁니다. agent가 청크 원문을 조회합니다 |
| 3-1 | 열어 본 청크가 근거로 부족할 때 | 라우터로 돌아가 다른 후보를 찾습니다 (상한 1회) |
| 4 | 끝까지 찾지 못했을 때 | **참조문서 없음**을 선택합니다. 억지로 맞추지 않고, 규정에 없다는 것과 담당 부서를 안내합니다 |

- 선택한 문서·도구 목록은 state에 저장하고, 역질문 후 다음 턴에도 다시 라우팅하지 않고 이어서 씁니다.

### 4.2 검색 방식

- **하이브리드**(BM25 + 벡터)로 시작합니다. 첫 단계 재현율이 전체 정확도를 좌우하는데, "기름값"과 "자동차 운임"처럼 사용자 표현과 규정 용어가 다른 경우를 BM25만으로는 놓치기 쉽기 때문입니다.
- 임베딩 대상은 문서 본문이 아니라 **용도 메타데이터**(`summary`·`keywords`·`questions`)입니다. 청크 단계 검색은 검증된 청크(본문 + 메타데이터)를 대상으로 합니다. 수치가 이미지에만 있는 PDF는 자동으로 자른 청크에서 숫자가 빠지기 때문입니다.
- 검색 도구 인터페이스(`search(query, category?)` → 문서·청크 목록)는 처음부터 고정해, 검색 엔진을 바꿔도 그래프는 그대로 두게 합니다.

### 4.3 카테고리

- **사용자 관점의 주제**로 나눕니다 (예: 출장·여비, 교육, 급여·세무). 부서 조직도로 나누지 않고, 담당 부서는 문서의 속성으로 둡니다. 사용자는 소관 부서를 모르는 경우가 많고(여비는 회계로 생각하기 쉽지만 담당은 상생복지팀), 조직 개편 때도 카테고리를 유지할 수 있습니다.
- 문서 하나가 여러 카테고리에 속할 수 있고, 라우터도 여러 카테고리를 고를 수 있습니다.
- 카테고리는 별도 LLM 단계가 아니라 **라우터 호출 안의 정보이자 검색이 빗나갔을 때의 두 번째 경로**입니다.
- **용도 목록 페이징은 쓰지 않습니다.** 페이지를 넘기느라 호출이 늘고, 페이지 사이의 문서를 비교할 수 없으며, 앞 페이지에서 그럴듯한 문서를 보면 멈추는 경향이 있기 때문입니다.
- 실제 분류는 100종 문서 목록이 확보되면 정합니다.

### 4.4 흐름도

```text
질의
 ├─ 범위 밖? ─────────────────────────────────────▶ 참조문서 없음 → 담당 부서 안내
 ▼
[라우터] 하이브리드 검색 → 후보 10~20개 (카테고리 표시)
 ▼
LLM 선택 (카테고리 목록 + 후보)
 ├─ 후보가 맞지 않음 → 카테고리 문서 목록 펼치기 ─┐
 ├─ 해당 없음 ───────────────────────────────────┼▶ 참조문서 없음 → 담당 부서 안내
 ▼                                               │
선택 문서 최대 3개 → state 저장 ◀─────────────────┘
 ▼
[planner] 선택 문서의 청크 목록 + 도구로 계획
 ▼
[agent] 청크 원문 조회 ── 근거 부족 → 라우터로 (1회)
 ▼
도구 호출 / 역질문 / 답변
```

## 5. 권장 전체 흐름

```text
질의 → [router] 하이브리드 검색 → 문서 최대 3개 선택 (카테고리 펼치기 / 참조문서 없음)
     → state에 selected_docs / tools / slots 저장
     → [planner] 선택 문서의 청크 목록·도구로 계획
     → [agent] get_chunks(ids) → 문서별 도구 바인딩 → 호출
          ↳ need_info → 역질문 (최대 2회) → 다음 턴은 같은 state로 재개
     → 근거(문서·청크·쪽) 표시하여 답변
```

### 5.1 결정 사항 요약

| 항목 | 결정 |
| :--- | :--- |
| 라우터 | planner와 분리된 별도 노드. 검색으로 좁힌 후보에서 LLM이 최대 3개 선택 |
| 카탈로그 저장소 | 실제 DB (문서·청크·도구·카테고리 테이블, 문서↔도구·문서↔카테고리 N:M). 검색 인덱스(BM25·벡터) 포함 |
| 검색 | 하이브리드(BM25 + 벡터), 임베딩 대상은 용도 메타데이터 |
| 역질문 | 최대 2회. 그래도 부족하면 "~인 경우 ○○, ~인 경우 △△"처럼 경우를 나눠 조건부로 답변 |

### 5.2 구현 순서

1. **임베딩 모델 확보**: 현재 DGX 서버에는 생성 모델만 있고 임베딩 모델이 없습니다. 한국어를 지원하는 임베딩 모델(예: bge-m3 계열)을 서버에 올리거나 로컬에서 실행합니다
2. **카탈로그 DB·스키마**: 문서·청크·도구·카테고리 테이블과 검색 인덱스. 기존 2종(교육훈련비, 여비)을 첫 데이터로 이관합니다
3. **메타데이터 작성 파이프라인**: LLM이 `summary`·`keywords`·`questions` 초안을 만들고 사람이 검증합니다
4. **검색 도구**: `search(query, category?)`, `list_docs(category)`, `get_chunks(ids)`를 MCP 서버에 추가합니다
5. **router 노드**: `graph.py`에 planner 앞 노드로 추가하고, 선택 결과를 state에 저장합니다
6. **문서별 도구 바인딩**: 선택된 문서의 도구만 agent에 바인딩합니다
7. **역질문 상한·조건부 답변**: state에 역질문 횟수를 두고 프롬프트 규칙에 반영합니다
8. **평가셋·회귀 측정**: §6 지표

## 6. 평가

[POLICY_KNOWLEDGE_INDEX.md §7](POLICY_KNOWLEDGE_INDEX.md)의 지표를 확장해서 사용합니다.

| 지표 | 정의 |
| :--- | :--- |
| 검색 재현율@20 | 하이브리드 검색 후보 20개 안에 기대 문서가 포함된 비율. 이 단계에서 빠지면 뒤에서 복구할 수 없으므로 가장 먼저 봅니다 |
| 문서 재현율@3 | 라우터가 선택한 문서(최대 3개)에 기대 문서가 포함된 비율 |
| 청크 재현율@3 | 선택한 청크(최대 3개)에 기대 청크가 포함된 비율 |
| 첫 도구 정확도 | 첫 도구 호출이 기대 도구와 일치하는 비율 |
| 역질문 적정성 | 정보가 부족한 질의에서 계산 대신 역질문을 한 비율 |
| 참조문서 없음 정확도 | 범위 밖·규정 공백 질의에서 억지 매칭 없이 "참조문서 없음"을 고른 비율 |
| 근거 표시율 | 규정 답변에 출처를 표시한 비율 |

- 헷갈리는 쌍(시내/시외 출장, 토익 학원비/토익 학점)과 **문서 두 개에 걸친 질의**를 평가셋에 반드시 넣습니다.
- 사용자 표현과 규정 용어가 다른 질의("기름값")를 넣어 벡터 검색이 실제로 보완하는지 확인합니다.
- 라우팅 정확도는 문서 수에 크게 좌우되므로, 2종으로 측정한 결과는 100종에서의 성능을 대표하지 못합니다. 실제 문서를 최소 수십 종 확보한 뒤 측정합니다.
