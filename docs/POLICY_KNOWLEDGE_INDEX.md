# 규정 지식 카드 및 목차 기반 조회 설계 (Policy Knowledge Index)

> ⚠️ **이전 단계 문서**. 사람이 만든 지식 카드와 목차 라우팅 설계로, 지금은 [RAG_DESIGN_NOTES.md](RAG_DESIGN_NOTES.md) §5.3의 자동 3계층(문서 요약 → parent → child)과 하이브리드 검색(dense + BM25, RRF)으로 바뀌었습니다. `get_policy` · `mcp_servers/` · `PLANNER_PROMPT` / `AGENT_PROMPT`에 기대는 절(§2, §4.2, §5, §6.2, §9)은 구현하지 않습니다. 지금 참조하는 부분은 §3.1 카드 작성 원칙, §7 라우팅 평가, §8 확장 방향입니다.

본 문서는 `docs/`의 사내 규정 PDF 2종을 **주제별 지식 카드**로 나누고, 카드에서 만든 **목차(Index)**를 에이전트가 보고 필요한 규정과 도구를 고르게 하는 방식을 정리한 문서입니다. 도구 명세는 [MCP_TOOL_DESIGN.md](MCP_TOOL_DESIGN.md)를 따르며, 본 문서는 그 도구들이 **어떤 규정을 근거로, 언제 호출되는지**를 찾아내는 조회 계층을 다룹니다.

- **목표**: 사용자 질의에 맞는 규정 원문을 정확히 찾아내고, 이를 근거로 올바른 계산·판단 도구를 선택하게 합니다.
- **핵심 아이디어**: 원문을 주제 단위 카드로 정리하고, 카드 메타데이터로 목차를 자동 생성합니다. LLM은 목차를 보고 카드 ID를 고른 뒤 본문을 조회합니다 (**목차 라우팅 → 원문 조회**의 2단계).

---

## 1. 방식 선택: 벡터 RAG 대신 목차 라우팅

| 검토 항목 | 일반 RAG (고정 길이 청크 + 임베딩 검색) | 목차 라우팅 (본 설계) |
| :--- | :--- | :--- |
| 문서 규모 (2p + 20p) | 검색 인프라 대비 문서가 너무 작습니다 | 목차가 약 1.5~3K 토큰이라 프롬프트에 그대로 넣을 수 있습니다 |
| 이미지로만 있는 수치 | 여비 PDF는 금액·거리가 텍스트 레이어에 없어서, 자동 청크에서는 **숫자가 빠집니다** | 사람이 옮기고 검증한 카드를 사용하므로 숫자가 보존됩니다 |
| 사용자 표현 ↔ 규정 용어 | "기름값"과 "자동차 운임"처럼 표현이 달라 임베딩 유사도가 낮게 나오기 쉽습니다 | 카드마다 `keywords`(동의어·구어 표현)를 명시하므로 매칭이 확실합니다 |
| 예외·단서 조항 | 청크 경계에서 본 조항과 예외가 분리되어 오답이 생깁니다 | 예외를 본 조항과 같은 카드에 두도록 강제합니다 |
| 도구 선택 | 검색 결과만으로는 어떤 도구를 쓸지 알 수 없습니다 | 목차에 `tools`가 붙어 있어 섹션과 도구를 함께 고릅니다 |
| 추적성 | 청크 출처가 불명확합니다 | 답변에 카드 ID와 원문 쪽을 근거로 표시할 수 있습니다 |

> 문서가 수십 종 이상으로 늘면 §8의 하이브리드 확장(BM25·임베딩으로 목차 후보를 먼저 좁힘)을 추가합니다. 이 경우에도 카드 구조는 그대로 사용합니다.

## 2. 전체 구조

```text
[원문 PDF] ──(1) 사람 검증 전사──▶ [지식 카드 docs/policy/*.md]
                                         │
                     ┌───────────────────┼─────────────────────┐
                (2) 목차 자동 생성       (3) 수치 테이블 추출      (4) 평가셋 추출
                     ▼                   ▼                     ▼
          [목차] → PLANNER/AGENT 프롬프트   계산 도구(T1~T5, E1~E2)   tests/routing_cases
                     │
   사용자 질의 → planner: 카드 ID + 도구 선택
              → agent: get_policy(ids)로 원문 확인 → 계산 도구 호출 → 근거(sources)와 함께 답변
```

- **단일 원천(Single Source of Truth)**: 규정 내용은 카드에만 둡니다. 목차, 조회 도구, 평가셋은 모두 카드에서 생성합니다.
- 수치 테이블(`mcp_servers/data/travel_rules.py` 예정)은 카드와 내용이 어긋나지 않도록 §6.2의 규칙을 따릅니다.

## 3. 지식 카드 작성 규칙

### 3.1 분할 원칙

| # | 원칙 | 설명 |
| :---: | :--- | :--- |
| 1 | **조항·주제 1개 = 카드 1개** | 글자 수로 자르지 않고 원문의 `Ⅲ-󰊲 시외당일귀임` 같은 의미 단위로 자릅니다. 한 카드가 다루는 질문 유형이 둘 이상이면 나눕니다 |
| 2 | **표는 쪼개지 않음** | 직급별 기준표, 국외 체재비표, 국가·도시 등급표는 각각 카드 하나에 통째로 둡니다 |
| 3 | **예외·단서는 본 조항과 함께** | "다만", "단", "※" 조항은 반드시 같은 카드에 둡니다 (예: 업무용 차량 이용 시 1만원 감액) |
| 4 | **자기완결성** | "위 제3항에 따라", "상기 기준" 같은 참조 표현은 실제 내용으로 풀어 씁니다. 카드 하나만 읽어도 답할 수 있어야 합니다 |
| 5 | **원문 우선, 요약은 분리** | 본문은 원문 문구를 유지합니다. 해석이나 요약은 `summary`에만 씁니다 |
| 6 | **수치는 검증 표시** | 이미지에서 옮긴 수치는 원문 대조를 마친 뒤 `verified: true`로 표시합니다. 미검증 카드는 조회 결과에 경고를 붙입니다 |
| 7 | **규정 공백 명시** | 규정에 없는 내용은 추측해서 채우지 않습니다. `gaps`에 적고 [MCP_TOOL_DESIGN.md §5](MCP_TOOL_DESIGN.md)와 연결합니다 |

권장 분량은 카드당 본문 200~1,200자입니다. 이보다 길면 분할 원칙 1을 다시 검토하되, 표가 포함된 카드는 예외로 둡니다.

### 3.2 카드 스키마

파일 위치는 `docs/policy/<doc>/<id>.md`이며, YAML frontmatter와 본문으로 구성합니다.

| 필드 | 필수 | 설명 | 예 |
| :--- | :---: | :--- | :--- |
| `id` | ✅ | `<문서>-<영역>-<번호>`. 바뀌지 않는 키입니다 | `TRV-DOM-07` |
| `doc` | ✅ | 원천 문서명·버전 | `여비업무 처리기준(250909)` |
| `path` | ✅ | 원문 목차 경로 | `Ⅲ 출장유형별 > 국내출장 > 자동차 운임` |
| `title` | ✅ | 목차에 표시할 제목 (15자 내외) | `자가용 운임 인정 사유` |
| `summary` | ✅ | 1~2문장 요약. 목차에 노출됩니다 | `원칙은 철도·버스 운임, 부득이한 사유가 있으면 연료비+통행료` |
| `keywords` | ✅ | 사용자가 실제로 쓸 동의어·구어 표현 | `[자차, 기름값, 유류비, 주유비, 개인차량]` |
| `questions` | ✅ | 이 카드로 답해야 하는 예상 질문 2~5개. 평가셋으로 재사용합니다 | `["자차로 갔는데 기름값 받아요?"]` |
| `tools` | | 이 카드를 근거로 쓰는 도구 | `[calculate_car_fare]` |
| `related` | | 함께 봐야 하는 카드 | `[TRV-REF-01]` |
| `pages` | ✅ | PDF 쪽번호 (표지 포함 1부터) | `[8]` |
| `effective_date` | | 수치의 기준일 | `2025-01-01` |
| `verified` | ✅ | 원문 대조 완료 여부 | `true` |
| `gaps` | | 규정 공백 | `["국외출장 식사 제공 시 감액 규정 없음"]` |

### 3.3 카드 예시

```markdown
---
id: TRV-DOM-07
doc: 여비업무 처리기준(250909)
path: Ⅲ 출장유형별 여비지급 기준 > 󰊴 국내출장 > 자동차 운임
title: 자가용 운임 인정 사유
summary: 자가용 운임은 원칙적으로 철도·버스 운임으로 지급하고, 공무상 부득이한 사유가 있으면 참고1에 따라 연료비와 통행료를 지급합니다.
keywords: [자차, 자가용, 기름값, 유류비, 주유비, 개인차량, 내 차]
questions:
  - 자차로 출장 갔는데 기름값 받을 수 있어요?
  - 버스가 없는 산업단지인데 자가용 써도 되나요?
  - 자가용 운임이랑 통행료 합쳐서 청구해도 돼요?
tools: [calculate_car_fare, calculate_domestic_trip_expense]
related: [TRV-REF-01]
pages: [8]
verified: false
---

○ 자동차 운임: 자가 승용차를 이용하여 공무로 여행하는 경우의 운임은 철도운임 또는 버스운임으로 함
 ∘ 다만, 공무의 형편상 부득이한 사유로 자가용을 이용한 경우 [참고1]에 따라 연료비 및 통행료를 지급할 수 있음
   * 연료비, 통행료 각 항목별 산정금액 내 지급 (연료비+통행료 합산금액 항목 교차지급 불가)

<공무형편상 부득이한 사유>
 ◦ 산간오지, 도서벽지 등 대중교통수단이 없어 자가용을 이용할 수밖에 없는 경우
 ◦ 출장경로가 매우 복잡·다양하여 대중교통을 사실상 이용할 수 없는 경우
 ◦ 공무목적상 부득이한 심야시간대 이동 또는 긴급한 사유가 있는 경우
 ◦ 하중이 무거운 수하물을 운송해야 하는 경우
 ◦ 기타: 자가용을 이용함으로써 운임이 적게 소요되는 경우, 대중교통 이용이 어려운 장애인 직원 등
 ∘ 특히, 대중교통 탑승 시 출장일정 소화가 불가하거나 철도 직행노선이 없어 대중교통 환승비가 자가용 운임보다 과다한 경우 자동차 운임으로 산출 가능
```

## 4. 목차 생성 및 프롬프트 주입

### 4.1 목차 형식

카드 frontmatter에서 한 줄씩 자동 생성합니다. 카드 본문은 넣지 않습니다.

```text
[규정 목차] 형식: ID | 제목 | 요약 | 키워드 | → 도구
EDU-EXC-01 | 지원 제외대상 | 취미·투자·취업준비·교재비만 지출 등은 지원 불가 | 필라테스, 주식, 공무원시험, NCS | → check_training_eligibility
TRV-DOM-01 | 시내출장 | 같은 시군, 왕복 12~120km 당일 귀임. 일비 1~2만원 정액 | 시내, 근거리, 4시간 | → calculate_domestic_trip_expense
```

- 카드 36개 × 약 50토큰이면 2K 토큰 내외입니다. 정적인 텍스트라 프롬프트 캐시에도 유리합니다.
- `summary`에는 판단에 결정적인 수치·조건을 넣습니다 (예: "왕복 12~120km"). 목차만 보고도 후보를 좁힐 수 있게 하기 위해서입니다.

## 5. 조회 도구

### 5.1 `get_policy` (신규, `get_training_policy`·`get_travel_policy` 통합)

| 인자 | 타입 | 설명 |
| :--- | :--- | :--- |
| `ids` | `list[str] \| None` | 조회할 카드 ID (최대 5개). `related`는 자동으로 펼치지 않고 목록만 알려줍니다 |
| `query` | `str \| None` | ID를 모를 때의 키워드 검색. `title`·`keywords`·`questions`를 대상으로 매칭하고 상위 3개를 반환합니다 |

응답 예시:

```json
{
  "cards": [
    {
      "id": "TRV-DOM-07",
      "title": "자가용 운임 인정 사유",
      "source": "여비업무 처리기준(250909) p8",
      "verified": true,
      "body": "○ 자동차 운임: ...",
      "related": ["TRV-REF-01"],
      "tools": ["calculate_car_fare"]
    }
  ],
  "not_found": []
}
```

- 존재하지 않는 ID는 `not_found`에 담고, 비슷한 ID나 제목을 제안합니다. LLM이 ID를 잘못 쓴 경우의 복구용입니다.
- 기존 `get_training_policy(section=...)`는 전환 기간 동안 `EDU-*` 카드로 위임하는 얇은 래퍼로 남겨 두고, 프롬프트 전환이 끝나면 제거합니다.

### 5.2 계산 도구 응답에 근거 추가

T1~T5, E1~E2의 결과에 `sources` 필드를 추가해서, 계산에 사용한 규칙의 카드 ID를 반환합니다.

```json
{ "status": "ok", "total": 35000, "sources": ["TRV-DOM-03", "TRV-DOM-11"], "basis": "..." }
```

이렇게 하면 LLM이 계산 결과와 근거 원문을 연결해서 설명할 수 있고, 오답이 나왔을 때 어느 카드나 어느 규칙이 원인인지 추적할 수 있습니다.

## 6. 카드와 계산 도구의 정합성

### 6.1 문제

같은 수치(예: 숙박 상한 서울 100,000원)가 카드 본문, [MCP_TOOL_DESIGN.md 부록 A](MCP_TOOL_DESIGN.md), 계산 도구 테이블의 세 곳에 존재하게 됩니다. 규정이 개정되면 어긋날 수 있습니다.

### 6.2 규칙

| # | 규칙 |
| :---: | :--- |
| 1 | 수치표가 있는 카드는 본문 아래에 기계가 읽을 수 있는 `data` 블록(YAML)을 둡니다. 계산 도구는 이 블록을 로드해서 사용합니다 |
| 2 | 부록 A는 카드가 완성되면 "카드 참조"로 바꾸고 수치는 삭제합니다 |
| 3 | 테스트에서 "카드의 `data` 블록 = 도구가 사용하는 값"을 검사합니다 |
| 4 | 규정 개정 시 `doc` 버전과 `effective_date`를 올리고, 바뀐 카드만 `verified: false`로 되돌려 재검증합니다 |

~~~~markdown
<!-- TRV-DOM-08 본문 아래 -->
```yaml data
lodging_cap: { 서울: 100000, 광역시: 80000, 기타: 70000 }
lodging_extra_rate: 0.3
lodging_own_or_relative: 20000
```
~~~~

## 7. 라우팅 평가

카드의 `questions`를 모아 **질의 → 기대 카드 ID·기대 도구** 테스트셋을 자동으로 만들고, 사람이 실제 문의 표현으로 20~30개를 보강합니다.

| 지표 | 정의 | 목표 (초기) |
| :--- | :--- | :---: |
| 카드 재현율@3 | planner가 고른 카드(최대 3개)에 기대 카드가 포함된 비율 | ≥ 90% |
| 도구 정확도 | 첫 도구 호출이 기대 도구와 일치하는 비율 | ≥ 90% |
| 역질문 적정성 | 슬롯이 부족한 질의에서 계산 대신 역질문을 한 비율 | ≥ 85% |
| 근거 표시율 | 규정 답변에 카드 출처를 표시한 비율 | ≥ 95% |

- 테스트셋에는 **헷갈리기 쉬운 쌍**을 일부러 넣습니다. 예: "같은 시인데 왕복 100km" (시내출장)와 "옆 시인데 왕복 100km" (시외당일귀임), "토익 학원비" (지원·과세)와 "토익 학점" (공통이라 학점 불가).
- 실패 사례는 대부분 `keywords`나 `summary`를 보강해서 해결합니다. 프롬프트 규칙을 늘리는 것보다 이쪽을 우선합니다.
- 프롬프트나 모델을 바꿀 때마다 같은 셋으로 회귀 측정합니다.

## 8. 확장 방향

| 시점 | 확장 |
| :--- | :--- |
| 문서 5종 이상 또는 목차 8K 토큰 초과 | 목차를 문서별 상위 목차와 카드 목차로 2계층화합니다. planner가 문서를 먼저 고르고, 선택된 문서의 카드 목차만 주입합니다 |
| 문서 수십 종 이상 | `get_policy(query)`를 BM25와 임베딩의 하이브리드 검색으로 교체해 목차 후보를 먼저 좁힙니다. 임베딩 대상은 본문이 아니라 `title + summary + keywords + questions`로 합니다 |
| 운영 로그 축적 | 실제 사용자 질의 중 매칭에 실패한 표현을 `keywords`·`questions`에 반영합니다 |
| 규정 개정 빈번 | PDF 신구대비표를 받아 바뀐 카드만 재검증하는 절차를 만듭니다 |

## 9. 구현 순서

1. **원문 전사**: 여비 PDF 20쪽을 페이지 이미지로 읽어 Markdown으로 옮깁니다. 텍스트 레이어에서 빠진 수치는 이미지에서 옮기고 원문과 대조합니다 (`qwen3.6:35b` Vision 또는 수작업).
2. **카드 분할**: §3.4 목록대로 `docs/policy/`에 카드를 작성합니다. 교육 6개는 기존 `TRAINING_POLICY`를 이관합니다.
3. **검증**: 담당자가 수치 카드를 원문과 대조하고 `verified: true`로 표시합니다.
4. **로더·목차 생성기**: `mcp_servers/policy_store.py`에서 카드를 파싱하고, 스키마 검증(필수 필드, ID 중복, `related` 링크 유효성)과 목차 문자열 생성을 담당합니다.
5. **도구 교체**: `docs_server.py`에 `get_policy`를 추가하고, `get_training_policy`를 래퍼로 전환합니다.
6. **프롬프트 반영**: `graph.py`의 `PLANNER_PROMPT`·`AGENT_PROMPT`에 목차와 §4.2 규칙을 주입합니다.
7. **평가셋·회귀 테스트**: §7 지표를 측정하는 스크립트를 만들고 기준선을 기록합니다.
8. **계산 도구 연동**: T1부터 카드 `data` 블록을 사용하도록 구현하고, 응답에 `sources`를 추가합니다.
